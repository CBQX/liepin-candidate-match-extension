# 猎聘候选人匹配分析插件设计

- 日期：2026-08-18
- 状态：已批准
- 当前阶段：C（可真实试用的 MVP）
- 后续阶段：A（内部稳定使用）→ B（多客户商业化）

> **存储方案补充（2026-08-18，取代第 11.1 节的原始 `chrome.storage.local` 持久化选择）：**
> 最终安全复审后，持久岗位与用户主动记住的模型设置改用扩展源 IndexedDB；
> `chrome.storage.session` 继续承载仅会话设置，`chrome.storage.local` 只作为旧版本迁移源。
> 原设计的产品阶段、BYOK 与“不持久化候选人”决策不变。

> **阶段 C 硬规则安全裁决（2026-08-18，取代第 9 节对年限、地点和证书进行确定性核验的原始设想）：**
> `years_experience`、`location` 和 `certificate` 的确定性硬规则状态一律为 `unknown`，
> 无论候选人原文或已提取事实呈现明确正向还是负向措辞。岗位条件、候选人原文和提取事实仍提供给模型并展示给猎头作为证据；相关已脱敏候选人来源证据由本地规则结果独立保存，即使模型遗漏也必须出现在最终报告并标注“需猎头核实”。证据内容或有无不得改变状态、硬条件降级、分数、可信度、推荐或淘汰结果。阶段 C 缺少受维护的结构化履历与凭证数据，自然语言中的范围、否定、计划、有效期、当前地点和到岗意愿又容易被误读；宁可增加人工核实成本，也不允许这些维度成为确定性门槛。学历等当前可安全结构化的维度保持原有规则行为。

## 1. 背景与目标

本项目为猎头提供一款优先兼容 Windows 与 macOS 版 Google Chrome 的浏览器插件。猎头先配置本次招聘的公司、职位 JD 和个性化要求，再打开猎聘中的单个候选人详情页，手动触发“匹配分析”。插件从当前页面提取候选人信息，经用户校对后，给出匹配度、匹配与不匹配理由、风险、信息缺口和猎头推进建议。

第一阶段的目标不是代替猎头决策，而是验证三个核心假设：

1. 插件能够较稳定地提取猎聘候选人详情页中的可见信息。
2. 混合评分结果足够可信、全面且可解释。
3. 该流程能够减少猎头初筛时间并改善沟通准备质量。

## 2. 产品阶段与范围

### 2.1 阶段 C：当前 MVP

- 纯 Chrome 插件，不部署产品后端。
- 默认接入 DeepSeek，用户自带 API Key。
- 设计统一模型接口，但当前只交付 DeepSeek 内置适配器。
- 岗位配置保存在浏览器本地。
- 候选人信息和分析结果不落库、不形成历史记录。
- 仅支持猎聘中用户主动打开的单个候选人详情页。
- 以 Chrome 侧边栏作为主要操作界面。

### 2.2 阶段 A：内部稳定使用

- 公司后端代理模型调用，插件不再接触模型密钥。
- 接入员工身份、统一配置和企业策略。
- 视内部政策决定是否增加受控的候选人分析历史。
- 提升猎聘页面适配、监控和故障反馈能力。

### 2.3 阶段 B：商业化产品

- 增加多租户、组织隔离、角色权限、额度与计费。
- 增加客户管理、审计、合规配置和多模型策略。
- 插件的页面提取、岗位领域模型、评分协议和侧边栏体验保持稳定。

## 3. MVP 非目标

MVP 不包含以下能力：

- 搜索结果列表批量分析。
- 自动翻页、自动点击、隐藏内容抓取或后台持续监控。
- 候选人分析历史、人才库或 CRM。
- Chrome 商店正式发布流程。
- Firefox、Safari 或 Edge 的专门适配。
- 账号、组织、权限、管理后台、用量统计或计费。
- 使用行为埋点、遥测或远程日志。
- 自动替代猎头作出录用或淘汰决定。

## 4. 核心用户流程

### 4.1 首次配置模型

1. 用户打开插件侧边栏。
2. 用户选择模型供应商；MVP 唯一内置供应商为 DeepSeek。
3. 用户填写 API Key。
4. 插件验证密钥和基础连通性。
5. 密钥默认只保留到当前 Chrome 会话结束；用户可以主动选择“记住此设备”。

### 4.2 添加岗位

1. 用户点击“添加新岗位”。
2. 用户填写公司、职位 JD 和个性化要求，三项均为必填。
3. 插件验证内容非空并保存岗位。
4. 新岗位成为“当前岗位”。
5. 插件提示“岗位已就绪，可以开始浏览候选人”。

### 4.3 分析候选人

1. 用户在猎聘中打开单个候选人详情页。
2. 用户在侧边栏点击“匹配分析”。
3. 插件读取当前页面的可见候选人信息。
4. 插件展示可编辑预览，并标记已提取、可能不完整和未找到的区域。
5. 用户修改或粘贴补充后点击“确认并分析”。
6. 插件执行规则预判，再调用 DeepSeek 进行结构化综合判断。
7. 插件校验模型结果、合成总分与推荐等级，并在侧边栏展示。

### 4.4 切换岗位

- 侧边栏顶部始终显示当前岗位。
- 用户可以从已保存岗位中直接切换，也可以点击“添加新岗位”。
- 同一时间只有一个当前岗位。
- 添加或切换岗位不会删除其他岗位。
- 切换完成后，下一次分析必须只使用新的当前岗位。

## 5. 侧边栏信息架构

侧边栏包含以下主要状态：

1. **模型设置**：供应商、API Key、会话保存或记住设备、验证状态。
2. **无岗位状态**：解释三项必填内容并引导添加岗位。
3. **岗位已就绪**：当前岗位、岗位切换、添加新岗位、匹配分析按钮。
4. **候选人校对**：按基本信息、工作经历、项目、教育、技能和其他内容分区编辑。
5. **分析中**：显示步骤和可取消操作，不展示未经校验的部分结论。
6. **分析结果**：展示总分、推荐等级、可信度、维度得分、证据、风险和建议。
7. **异常状态**：展示可操作的原因、保留用户已校对内容并允许重试。

工具栏插件图标只负责打开侧边栏。主要操作不放在容易因网页点击而关闭的传统弹窗中。

## 6. 技术架构

### 6.1 平台与技术栈

- Chrome Manifest V3。
- 最低 Chrome 版本为 116。
- TypeScript + React 构建侧边栏。
- Vite 负责开发与打包。
- Chrome Side Panel API 提供持续可见界面。
- Chrome Service Worker 负责消息协调、模型调用和持久化访问。
- 运行时结构校验用于防止无效模型结果进入界面。

Chrome Side Panel API 在 Chrome 114+ 可用；`sidePanel.open()` 在 Chrome 116+ 可用，因此 MVP 将 Chrome 116 作为最低支持版本。Windows 与 macOS 使用相同的扩展代码和构建产物。

### 6.2 模块边界

```text
sidepanel/        侧边栏页面、交互状态和结果展示
content/          猎聘页面识别、候选人信息提取和文本兜底
background/       Service Worker、消息协调、模型请求和错误映射
domain/jobs/      岗位实体、校验、当前岗位和岗位切换
domain/matching/  规则评分、权重合成、推荐等级和可信度
providers/        ModelProvider 接口与 DeepSeek 适配器
repositories/     JobRepository、扩展源 IndexedDB、会话存储与旧数据迁移适配器
shared/contracts/ 跨模块消息、候选人草稿和分析结果协议
```

每个模块的职责边界如下：

- `content` 只将易变的猎聘 DOM 转换为稳定的候选人草稿，不负责评分或模型调用。
- `domain` 不依赖 Chrome API、React 或具体模型供应商，可独立测试。
- `providers` 将统一请求转换为供应商 API，并将结果规范化。
- `repositories` 隐藏存储实现，使阶段 A/B 能替换为远程仓库。
- `sidepanel` 只消费稳定协议，不读取猎聘 DOM，也不拼接供应商专用请求。

### 6.3 一次分析的数据流

```text
用户点击匹配分析
  → Side Panel 向 Service Worker 发出请求
  → Service Worker 请求当前标签页 Content Script 提取信息
  → Content Script 返回 CandidateDraft
  → Side Panel 展示可编辑预览
  → 用户确认
  → 规则引擎检查客观条件
  → ModelProvider 调用 DeepSeek
  → 运行时协议校验与一次修复重试
  → MatchComposer 合成分数、等级和可信度
  → Side Panel 展示结果
```

## 7. 核心数据协议

### 7.1 Job

```ts
interface Job {
  id: string;
  company: string;
  jd: string;
  customRequirements: string;
  createdAt: string;
  updatedAt: string;
}
```

当前岗位 ID 单独保存，避免通过数组顺序推断状态。所有写入均经过三项必填校验。

### 7.2 CandidateDraft

```ts
interface CandidateDraft {
  basics: ExtractedSection;
  workExperience: ExtractedSection;
  projects: ExtractedSection;
  education: ExtractedSection;
  skills: ExtractedSection;
  other: ExtractedSection;
  extractionConfidence: "high" | "medium" | "low";
}

interface ExtractedSection {
  text: string;
  status: "complete" | "possibly_incomplete" | "missing";
}
```

该对象只存在于本次分析的内存状态中，不写入持久化存储。提交给模型前移除手机号、邮箱、即时通信账号等直接联系方式，并将姓名替换为中性占位符。页面 URL 和猎聘候选人标识不发送给模型。

### 7.3 ModelProvider

```ts
interface ModelProvider {
  validateCredentials(settings: ProviderSettings): Promise<void>;
  analyze(input: MatchInput): Promise<ModelMatchResult>;
}
```

MVP 实现 `DeepSeekProvider`。后续供应商通过注册新适配器加入，侧边栏、评分引擎和结果协议无需变化。

### 7.4 MatchAnalysis

结果协议至少包含：

- `overallScore`：0–100 整数。
- `recommendation`：强推荐、建议推进、谨慎推进、暂不推荐。
- `confidence`：高、中、低。
- `dimensionScores`：各维度分数、权重和证据。
- `hardRequirements`：满足、不满足、未知及依据。
- `matches`：明确匹配项。
- `mismatches`：明确不匹配项。
- `risks`：稳定性、职级、经历断层等风险。
- `missingInformation`：未知信息和影响。
- `verificationQuestions`：电话或面试需要核实的问题。
- `outreachAdvice`：沟通切入点和职位卖点。
- `recruiterConclusion`：猎头角度的下一步建议。

所有结论必须引用岗位要求与候选人材料中的证据。运行时校验拒绝超范围分数、缺失必填字段和不受支持的枚举值。

## 8. 猎聘页面提取策略

提取器采用三层策略：

1. **结构化选择器层**：读取已知候选人详情区域和字段。
2. **语义标题层**：根据基本信息、工作经历、项目、教育、技能等可见标题组织内容。
3. **可见文本兜底层**：无法稳定识别结构时，返回当前页面可见简历文本供用户编辑。

设计约束：

- 只在用户点击“匹配分析”后执行。
- 只读取用户当前打开并可见的候选人详情信息。
- 不自动点击、不展开隐藏内容、不翻页、不批量处理。
- 不把“未找到”自动转换为“不满足”。
- 提取结果必须经过用户确认后才提交给模型。
- 页面改版时允许降级使用，不允许静默生成低可信结果。

## 9. 混合评分设计

### 9.1 岗位要求优先级

- 明确包含“必须、硬性、不接受”等表述的要求标记为硬性条件。
- 包含“优先、加分、最好具备”等表述的要求标记为偏好条件。
- 个性化要求优先于普通 JD 描述。
- 系统不得根据公司或职位名称自行创造未写明的隐藏要求。

### 9.2 默认权重

| 维度 | 权重 | 判断范围 |
|---|---:|---|
| 硬性条件 | 25% | 学历等可安全结构化的确定性核验；年限、地点、证书仅供模型分析与猎头核实 |
| 职能经验与专业能力 | 25% | 核心技能、岗位职责、相关项目 |
| 行业与业务匹配 | 15% | 行业背景、业务模式、客户类型 |
| 职级、管理跨度与成果 | 15% | 团队规模、决策范围、量化业绩 |
| 职业轨迹与稳定性 | 10% | 晋升、跳槽频率、经历连贯性 |
| 猎头推进可行性 | 10% | 候选人卖点、潜在顾虑、沟通切入点 |

各维度先计算 0–100 分，再按权重合成总分。MVP 使用固定默认权重，不提供用户自定义权重界面。

### 9.3 推荐等级与硬性条件

- 85–100：强推荐。
- 70–84：建议推进。
- 55–69：谨慎推进。
- 0–54：暂不推荐。

当前可安全结构化的确定性硬规则明确不满足时仍保留综合分，以便猎头理解其他优势，但推荐等级至少降一级且不能为“强推荐”。存在多个这类关键硬性条件不满足时，推荐等级为“暂不推荐”。阶段 C 中地点、工作年限和证书的本地规则一律为“未知”；本地保留的已脱敏候选人来源证据与模型引用证据分开呈现，前者即使模型遗漏也保留，但两者都不能把这些维度写回为确定性 `met`/`not_met` 或触发自动降级。

未知信息不扣匹配分，但降低分析可信度。关键区域完整、证据充分时为高可信；存在影响结论的重要未知项时为中可信；核心经历或多项硬条件无法判断时为低可信。

### 9.4 证据规则

- 每个匹配或不匹配结论都必须附岗位侧依据和候选人侧依据。
- 不允许用年龄、性别、民族、婚育等受保护或与岗位无关的个人特征评分。
- 不允许把模型推测写成候选人事实。
- 稳定性判断需要展示任职时间证据，并同时指出可能存在的信息缺口。
- 信息不足时优先生成核实问题，而不是生成确定结论。

## 10. 模型接入

### 10.1 MVP DeepSeek 调用

- 使用 HTTPS 调用 DeepSeek Chat Completions API。
- 请求启用 JSON 输出模式。
- 系统提示词明确要求返回 JSON，并给出目标结构示例。
- 设置足够的输出上限，检查响应是否因长度截断。
- 对模型结果执行本地协议校验。

DeepSeek 官方提示 JSON 输出可能偶发空内容。MVP 对空响应、格式错误或截断执行一次自动重试或修复请求；第二次仍失败则停止，不展示不完整分数，并保留用户校对内容供重试。

### 10.2 多模型扩展

模型设置界面与 `ModelProvider` 注册表分离。阶段 C 只注册 DeepSeek；后续可以增加 OpenAI、通义千问、豆包或其他兼容服务。每个适配器负责：

- 凭证验证。
- 域名和模型配置。
- 请求参数转换。
- 供应商错误转换为统一错误。
- 响应转换为统一结果协议。

## 11. 存储、权限与隐私

### 11.1 持久化数据

原始批准设计选择用 `chrome.storage.local` 保存岗位、当前岗位 ID、模型供应商选择，以及用户主动选择“记住此设备”时的 API Key。该具体介质选择已由本节开头所述的最终安全复审决定取代；保留此说明是为了准确记录设计演进，而不是继续指导实现。

当前实现使用扩展源 IndexedDB 保存：

- 岗位列表。
- 当前岗位 ID。
- 用户主动选择“记住此设备”时的模型供应商、模型与 API Key。

`chrome.storage.session` 保存未勾选“记住此设备”时的会话级模型设置与 API Key。`chrome.storage.local` 不再承担正常持久化，只在升级时读取旧版的 `jobs`、`activeJobId` 和 `providerSettings`；迁移以单个 IndexedDB 读写事务执行“仅缺失写入 + 幂等标记”，成功后只删除这三个旧键，不覆盖更新的 IndexedDB 值。

候选人草稿、姓名脱敏上下文和分析结果只在当前界面内存中存在，不写入 `storage.local`、`storage.session`、`storage.sync`、IndexedDB 或日志。

选择扩展源 IndexedDB 是 Chrome 116 的纵深隐私边界：`chrome.storage.local` 默认可供 Content Script 使用，虽然可以调用 `setAccessLevel()` 收窄访问，但仍依赖正确初始化；扩展页面和 Service Worker 共享扩展源 IndexedDB，而 Content Script 调用 Web Storage/IndexedDB 时使用所在猎聘页面的源，不能直接打开扩展源数据库。`chrome.storage.session` 保持可信上下文访问。由此 Content Script 无权直接读取岗位或 API Key。

### 11.2 权限

MVP 只申请完成任务所需的权限：

- `sidePanel`：显示侧边栏。
- `storage`：保存岗位和模型设置。
- 猎聘域名权限：只用于用户触发后的当前页面提取。
- DeepSeek 域名权限：只用于用户确认后的模型调用。

后续模型域名以可选权限方式按供应商申请，不预先申请无关网站访问权限。

### 11.3 隐私提示

- 首次提交候选人内容给 DeepSeek 前，明确说明将向第三方模型服务发送哪些类型的数据。
- API Key 默认不长期持久化。
- 若用户选择本地记住密钥，界面明确说明扩展本地存储未加密。
- 不收集遥测、浏览历史或分析日志。
- 内部推广前需由公司确认猎聘使用规则、候选人数据处理政策和第三方模型使用政策。

## 12. 异常处理

| 场景 | 行为 |
|---|---|
| 当前页面不是候选人详情页 | 提示打开单个候选人详情页，不发起模型调用 |
| 页面提取不完整 | 进入可编辑预览并标记缺失，不直接分析 |
| API Key 缺失或无效 | 引导配置或重新验证 |
| 模型超时、限流或余额不足 | 保留已校对内容，展示明确原因并允许重试 |
| 模型返回空内容或格式错误 | 自动修复一次；仍失败则停止展示结果 |
| 页面结构变化 | 使用可见文本兜底并降低提取可信度 |
| 用户切换岗位 | 清除当前候选人草稿和结果，防止岗位串用 |
| 页面跳转、刷新或结束分析 | 清除候选人草稿和结果 |
| 存储写入失败 | 保留表单内容，提示用户重试，不显示保存成功 |

异常信息使用用户可理解的语言，同时保留内部错误代码供本地调试，但不记录候选人内容或 API Key。

## 13. 测试策略

### 13.1 单元测试

- 三项岗位必填校验。
- 岗位新增和当前岗位切换。
- 规则状态：满足、不满足和未知。
- 权重合成、分数边界和推荐等级降级。
- 可信度计算。
- 运行时结果协议校验。
- 候选人内存数据清除。

### 13.2 提取器夹具测试

使用脱敏页面样本覆盖：

- 完整候选人详情。
- 缺少教育或项目经历。
- 不同顺序和标题。
- 页面结构变更。
- 只有可见文本兜底可用。

### 13.3 模型契约测试

模拟以下 DeepSeek 响应：

- 正常结构化 JSON。
- 空响应。
- 非法 JSON。
- 缺少字段或分数越界。
- 长度截断。
- 超时、限流、余额不足和鉴权失败。

### 13.4 浏览器流程测试

覆盖首次设置、添加岗位、侧边栏打开、页面提取、信息校对、模型调用、结果展示、错误重试、岗位切换和数据清除。自动化测试之外，在 Windows 与 macOS 的 Chrome 上分别进行一次真实安装验收。

## 14. MVP 可行性验收标准

1. 使用至少 3 类岗位和 30 份脱敏候选人页面进行试用。
2. 至少 90% 的候选人详情页可以进入信息校对步骤。
3. 至少 80% 的样本中，基本信息、工作经历、项目和教育等核心区域无需整段重新粘贴。
4. 所有成功分析都包含总分、维度得分、证据、风险、信息缺口和猎头建议。
5. 未知信息不会被描述为明确不满足。
6. 明确违反当前支持确定性核验的硬性条件（阶段 C 当前为学历等可安全结构化维度）时，推荐等级自动降级；地点、工作年限和证书始终为“未知”，不会自动满足、淘汰或降级，但原文仍进入模型分析并供猎头核实。
7. 模型异常不丢失用户已经校对的候选人内容。
8. 切换岗位后不得继续引用旧岗位。
9. 页面刷新或结束分析后，本地持久化存储中不存在候选人资料和分析结果。
10. 试用猎头对每次输出标记“有帮助”或“无帮助”；至少 80% 的输出被标记为“方向正确且能辅助判断是否联系”，并记录其余输出的误判原因用于第二阶段改进。

## 15. 主要风险与缓解措施

| 风险 | 缓解措施 |
|---|---|
| 猎聘 DOM 更新导致提取失败 | 提取器与业务隔离、语义层和可见文本兜底、夹具回归测试 |
| 模型生成无依据结论 | 强制证据字段、未知状态、运行时校验和人工校对 |
| API Key 在客户端暴露 | 默认会话保存、可信上下文访问、明确风险提示、阶段 A 迁移后端 |
| 候选人信息发送到第三方模型 | 最小化和去除直接联系方式、提交前确认、内部政策审查 |
| 分数给猎头造成虚假确定性 | 同时展示推荐等级、可信度、证据和信息缺口 |
| 过早建设商业基础设施 | 阶段 C 只实现核心闭环，通过接口边界保留升级路径 |

## 16. 已确认决策摘要

- 当前先做 C，短期进入 A，长期演进到 B。
- MVP 采用纯插件方案，并保留可替换边界。
- 默认 DeepSeek，统一模型适配接口。
- 第一阶段用户自带 Key；第二阶段迁移公司后端。
- 自动提取、可编辑预览和手动粘贴兜底。
- 不保存候选人分析历史。
- 混合评分，不使用纯模型自由打分。
- 只支持单个候选人详情页，不做批量自动化。
- 使用浏览器侧边栏作为主界面。
- 保存多个岗位，同一时间只有一个当前岗位。
- 最低支持 Chrome 116，Windows 与 macOS 共用构建。
- API Key 默认保存于 `chrome.storage.session`；用户主动选择本地记住时保存于扩展源 IndexedDB。

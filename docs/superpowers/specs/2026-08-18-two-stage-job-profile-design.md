# 两阶段岗位画像与候选人匹配设计

**日期：** 2026-08-18  
**状态：** 岗位画像部分继续有效；候选人输出与评分部分已被 `2026-08-19-lightweight-candidate-analysis-design.md` 取代
**适用阶段：** 阶段 C 内部可行性验证，并保持向阶段 A、B 升级的可替换边界

## 1. 决策摘要

把现有“每次候选人分析时同时理解岗位和候选人”的单阶段流程拆成两阶段：

1. 用户输入公司、职位 JD 和个性化要求，AI 只生成一次结构化岗位画像。
2. 用户逐条编辑、增加、删除要求并调整“硬性 / 优先 / 普通”，确认一次后长期保存。
3. 后续每位候选人只与这份已确认岗位画像比较，不再重复发送完整原始 JD 让模型重新理解。

候选人最终结果继续使用 0–100 分，并只提供联系建议，不引入淘汰、一票否决或单独的淘汰状态。AI 自动决定要求权重，插件把权重归一化为总计 100；本轮不增加人工配置权重的复杂界面。该决定取代原设计中“固定六维权重”和“确定性硬条件自动降级”的候选人推荐行为，但保留未知信息不扣分、证据约束和人工核实原则。

## 2. 目标与非目标

### 2.1 目标

- 把岗位理解成本从“每位候选人一次”降为“每个岗位一次”。
- 让同一岗位的所有候选人使用同一份由猎头确认的招聘标准。
- 缩短后续候选人的模型输入，降低超时、格式错误和判断漂移概率。
- 让用户在候选人分析前纠正 AI 对 JD 的误读。
- 保存已确认岗位画像，Chrome 重启后无需再次生成。
- 保持 DeepSeek 为早期默认实现，同时通过供应商中立接口支持未来增加其他模型。

### 2.2 非目标

- 不承诺第一位候选人的总耗时一定下降；创建岗位时会新增一次岗位画像调用。
- 不用这一改造掩盖网络、代理、余额、API Key、模型可用性或猎聘页面提取故障。
- 不批量抓取候选人、不自动翻页、不保存候选人历史。
- 不增加淘汰、一票否决或自动拒绝候选人的功能。
- 本轮不让用户手工维护总和为 100 的复杂权重表。

## 3. 用户流程

### 3.1 新建岗位

1. 用户完成模型设置。
2. 用户点击“添加新岗位”，填写公司、职位 JD 和个性化要求；三项仍为必填。
3. 用户点击“分析岗位要求”。插件保存不可用于候选人分析的原始岗位草稿，并发起岗位画像请求。
4. 界面显示“正在分析岗位…”，允许取消。
5. AI 返回结构化岗位画像；协议校验失败时自动执行一次修复请求。
6. 成功后进入“确认招聘关键要求”页面。
7. 用户可以编辑岗位名称、岗位目标、替代经验、信息缺口和核实问题；可以逐条编辑、新增、删除招聘要求，并调整每条要求的优先级和所属匹配维度。AI 已生成的维度默认无需用户改动。
8. AI 生成每条要求的相对权重，插件归一化为总计 100。权重在本轮可展示但不提供复杂手工配置。
9. 用户点击一次“确认岗位画像”。确认后的画像与岗位一起持久保存，新岗位成为当前岗位。
10. 插件提示“岗位画像已确认，可以开始浏览候选人”。

### 3.2 分析候选人

1. 用户在一个已确认岗位下主动打开猎聘单候选人详情页。
2. 用户点击“匹配分析”，校对并确认已脱敏候选人草稿。
3. 插件只向模型发送已确认岗位画像与已脱敏候选人草稿；不再发送完整原始 JD、个性化要求、重复条件或本地规则辅助信息。
4. 模型使用 V4 Flash 返回轻量证据化分析，直接给出 0–100 综合分、三档联系建议、主要理由、顾虑或信息缺口、核实问题和猎头结论。
5. 同一岗位的下一位候选人直接复用已确认画像，不再次生成岗位画像。

### 3.3 切换与重新分析岗位

- 切换到已确认岗位后可立即分析候选人，并清除上一岗位的候选人临时状态。
- 切换到没有画像的旧岗位或未确认岗位时，显示“需要生成岗位画像”，禁止候选人分析。
- 用户可主动点击“重新分析岗位”。生成和编辑新画像期间，原已确认画像继续有效。
- 只有用户确认新画像后才原子替换旧画像；取消或失败不会破坏旧画像。
- 岗位画像确认一次即可长期使用。再次确认只发生在用户主动重新分析并准备替换画像时。

## 4. 岗位画像协议

```ts
type RequirementPriority = "hard" | "preferred" | "standard";
type MatchDimensionId =
  | "hard_requirements"
  | "functional_expertise"
  | "industry_business"
  | "seniority_impact"
  | "trajectory_stability"
  | "recruiter_feasibility";

interface RecruitmentRequirement {
  id: string;
  text: string;
  priority: RequirementPriority;
  dimensionId: MatchDimensionId;
  weight: number;
  jobEvidence: string[];
}

interface ConfirmedRecruitmentProfile {
  version: 1;
  roleTitle: string;
  roleObjective: string;
  requirements: RecruitmentRequirement[];
  acceptableAlternatives: string[];
  ambiguities: string[];
  verificationQuestions: string[];
  confirmedAt: string;
}

interface Job {
  id: string;
  company: string;
  jd: string;
  customRequirements: string;
  recruitmentProfile?: ConfirmedRecruitmentProfile;
  createdAt: string;
  updatedAt: string;
}
```

协议约束：

- 岗位名称、岗位目标和招聘要求列表不能为空。
- 每条要求的文本、优先级、所属匹配维度、权重和至少一条岗位依据必须存在。
- AI 只能整理公司、JD 和个性化要求中有明确依据的招聘条件，不得根据公司或职位名称创造隐藏要求；推断出的替代经验必须单独放入 `acceptableAlternatives`，经用户确认后才生效。
- 权重必须是有限非负数；插件按比例归一化并以总计 100 保存，处理小数舍入后仍保证精确总和。
- 用户编辑既有要求时保留 AI 给出的相对权重；删除要求后对剩余权重重新归一化。用户新增要求时，初始相对权重取同优先级既有要求的中位数；若该优先级尚无要求，则依次使用 `hard = 3`、`preferred = 2`、`standard = 1`，再统一归一化。这样新增内容会参与评分，同时不要求第二次模型调用或人工维护百分比。
- 岗位画像不得包含年龄、性别、民族、婚育等受保护特征，模型返回此类要求时协议层必须拒绝。
- `hard` 只表示最高评分重要性，不代表一票否决、自动淘汰或推荐等级上限。
- AI 生成的草稿在确认前不得成为候选人评分依据。
- 原始公司、JD 和个性化要求继续保存，以便审计岗位依据和用户主动重新分析；候选人调用不携带这些原始长文本。

## 5. 评分与联系建议

本节原有的六维本地合成、可信度和四档建议设计已废止。当前候选人协议、评分规则、三档联系建议、证据边界与 Flash 模型策略以 [`2026-08-19-lightweight-candidate-analysis-design.md`](./2026-08-19-lightweight-candidate-analysis-design.md) 为准。

## 6. 组件与接口边界

### 6.1 岗位领域与仓库

- `Job` 增加可选的已确认 `recruitmentProfile`，使旧岗位可以安全读取。
- `JobService` 增加保存原始草稿、确认画像和原子替换画像的操作。
- `JobRepository` 继续隐藏 IndexedDB 实现；确认画像与岗位一起持久化，不增加候选人仓库。
- 老版本岗位数组不需要破坏性迁移：缺少画像即表示 `needs_profile`。

### 6.2 模型供应商

供应商接口拆成两个独立能力：

```ts
interface ModelProvider {
  validateCredentials(settings: ProviderSettings): Promise<void>;
  generateRecruitmentProfile(
    input: JobProfileInput,
    settings: ProviderSettings,
    signal?: AbortSignal
  ): Promise<ModelRecruitmentProfile>;
  analyzeCandidate(
    input: CandidateMatchInput,
    settings: ProviderSettings,
    signal?: AbortSignal
  ): Promise<ModelMatchResult>;
}
```

DeepSeek 适配器分别拥有岗位画像提示词和候选人提示词。供应商负责请求转换、响应提取与统一错误映射；岗位画像权重归一化与持久化属于扩展本地领域层，候选人综合分与联系建议则由模型直接返回并经本地协议校验。第二个模拟供应商契约测试必须证明 UI 和领域层不依赖 DeepSeek 特有字段。

### 6.3 Service Worker 协议

新增独立请求与取消边界：

- `GENERATE_JOB_PROFILE`
- `CANCEL_JOB_PROFILE`
- `CONFIRM_JOB_PROFILE`
- 现有候选人分析请求继续使用独立请求 ID

岗位画像请求与候选人请求不得共享进行中状态。二者都沿用真实 `AbortSignal` 取消、25 秒首包与正文阶段超时、统一错误码以及晚到响应忽略机制。

### 6.4 侧边栏状态

新增岗位流程状态：

- `job_form`
- `job_profile_analyzing`
- `job_profile_review`
- `job_profile_error`
- `job_ready`

候选人预览、分析和结果仍属于瞬态会话。岗位切换时清除候选人状态，但不清除任何已确认画像。

## 7. 错误处理与恢复

- 未配置或失效 Key：进入模型重新配置入口，并保留原始岗位输入或岗位画像编辑稿。
- 网络、代理、防火墙、限流、余额不足或超时：显示供应商中立的可操作错误，允许重试。
- 岗位画像输出为空、截断或不符合协议：自动修复一次；第二次失败后不显示或保存半成品画像。
- 用户取消：通知 Service Worker 终止对应请求，保留岗位原始输入；晚到结果不得恢复旧状态。
- 存储失败：不得显示“已确认”，保留编辑内容并允许重新保存。
- 重新分析失败：继续使用旧的已确认画像，不改变当前岗位可用状态。
- 候选人分析失败：保留已确认岗位画像和候选人校对内容，允许直接重试。

## 8. 隐私与安全

- 公司、JD、个性化要求和已确认岗位画像属于岗位配置，允许保存在扩展源 IndexedDB。
- 候选人草稿、脱敏上下文、分析输入和分析结果仍只存在于内存，不进入 IndexedDB、`chrome.storage`、日志、遥测或分析系统。
- 岗位画像提示词不得包含候选人信息；候选人提示词不得包含页面 URL、猎聘 ID、姓名或联系方式。
- 自动化测试只使用虚构公司、虚构 JD、虚构候选人和虚构猎聘标识。
- 截图和真实候选人信息不得写入代码、测试、文档、日志或交付 ZIP。

## 9. 测试策略

### 9.1 合成测试数据

构造至少三类虚构岗位，例如企业软件产品、海外产品和数据平台岗位；为每类岗位构造完全匹配、部分匹配、明显缺口、信息缺失和材料矛盾的虚构候选人。所有姓名、公司、履历、联系方式和标识均为合成数据。

### 9.2 自动化覆盖

- 岗位画像协议、受保护特征拒绝和权重精确归一化。
- 岗位画像生成、格式修复一次、取消、超时和供应商错误映射。
- 用户逐条编辑、新增、删除要求和调整优先级。
- 未确认画像禁止候选人分析，确认成功后跨仓库重建仍可读取。
- 多位候选人复用同一画像，岗位画像生成调用只发生一次。
- 候选人供应商输入不包含原始 `jd`、`customRequirements` 或其他岗位长文本，只包含已确认画像。
- 切换岗位、重新分析失败和原子替换不会串用或丢失岗位画像。
- 旧岗位缺少画像时显示迁移入口且原始字段不丢失。
- 候选人瞬态数据、取消语义、隐私脱敏和本地证据隔离不发生回归。
- DeepSeek 适配器与第二个模拟供应商通过相同契约测试。
- 完整流程：模型设置 → 新建岗位 → 生成画像 → 编辑确认 → 提取候选人 → 校对 → 100 分匹配 → 联系建议 → 第二位候选人复用画像。

### 9.3 交付与真实验收分工

Codex 负责合成数据自动化测试、模拟端到端测试、类型检查、生产构建、ZIP 完整性和静态隐私检查。用户负责在授权环境手动验收 Windows/macOS Chrome、真实 DeepSeek、真实猎聘页面和实际招聘判断。

真实验收继续采用 3 个岗位、每个岗位 10 位已授权候选人，记录岗位画像首次生成成功率、候选人分析成功率、第一位与后续候选人耗时、同岗位标准一致性和联系建议有用率。未完成真实验收前，不把本版本标记为阶段 A 或正式产品。

## 10. 性能预期与观测

- 岗位画像生成每个岗位只发生一次，除非用户主动重新分析。
- 第二位及以后候选人不再承担完整 JD 的重复解释成本，候选人请求的岗位侧输入应明显短于当前版本。
- 第一位候选人的“岗位创建 + 候选人匹配”总耗时可能相近或更长，不作下降承诺。
- 生产代码不记录候选人文本或模型响应。性能只记录用户手动验收表中的匿名耗时，不增加遥测。
- 若候选人分析仍失败，必须按网络、认证、余额、超时、无效模型输出或页面提取分别定位，不能笼统归因于岗位画像。
